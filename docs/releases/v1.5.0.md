# Garmin Running Workouts Import 1.5.0

Version 1.5.0 makes the transition between training blocks explicit and adds Garmin two-factor authentication while
preserving the existing password and reusable-token login paths.

## Highlights

- **One clear next step after a finished block:** the dashboard and interactive CLI detect when an applied block has
  no remaining workouts and offer **Generate next training block** instead of the mid-block adaptation action.
- **Evidence-led continuation:** generating the next block first refreshes completed runs, retrieves the recent Garmin
  and FIT evidence selected by the existing assessment workflow, and creates a new proposal from the active goal and
  preferences. The new block starts after the previous one.
- **Preview and approval remain mandatory:** generation does not change Garmin. The runner reviews the proposed
  workouts before explicitly approving upload and calendar scheduling.
- **Goal changes stay intentional:** the finished-block dashboard links directly to goal editing for runners who want
  to change direction before generating the next block.
- **Garmin two-factor authentication:** when Garmin requests an authenticator, email, or SMS verification code, the
  CLI displays a hidden code prompt and the web interface opens a dedicated verification step.
- **Short-lived web MFA state:** a pending web login stays only in server memory, is scoped to the initiating browser,
  expires after five minutes, and allows at most three code attempts. Passwords and verification codes are not stored.
- **Updated documentation:** the anonymized dashboard screenshot now shows a finished block and the prominent action
  that continues planning.

## Starting the next block

After the last scheduled workout has been completed or missed, refresh completed runs if needed and open the
dashboard. The block is labelled **Finished block**, the next-workout card says **Ready for the next block**, and the
primary action becomes **Generate next training block**.

Selecting that action performs the Garmin/FIT assessment and opens a proposal review. Nothing is uploaded until the
proposal is approved. If the training objective, availability, long-run day, heart-rate guidance, or constraints
should change, use **Edit the goal first** before generating the proposal.

The interactive CLI presents the equivalent **Generate the next training block** action when it detects the same
finished state.

## Garmin verification codes

Normal reusable-token and password logins work as before. If Garmin explicitly requests another verification step:

- complete the prompt using the most recent authenticator, email, or SMS code;
- keep the web deployment at one Gunicorn worker so both requests reach the same in-memory pending login;
- restart the login with the password if the pending request expires, the service restarts, or three codes are
  rejected.

An HTTP 429 response is still handled as Garmin rate limiting, not as an MFA challenge. The existing persistent
cooldown remains in effect and no automatic retry is attempted.

## Compatibility

- No database migration and no new runtime dependencies.
- Existing goals, plans, progress, FIT files, credentials, and scheduled workouts are retained.
- CLI commands and YAML formats remain compatible. Python 3.12 through 3.14 are supported.
- The application remains a single-runner tool and should stay behind the documented authenticated TLS reverse proxy.

## Upgrade

For an existing deployment following `main`:

```shell
git switch main
git pull --ff-only origin main
uv sync --no-dev --locked
sudo systemctl restart garmin-running-workouts-web.service
```

Use your actual service name if it differs from the supplied example. CLI-only installations do not need a service
restart.

To pin exactly this release instead:

```shell
git fetch origin --tags
git switch --detach v1.5.0
uv sync --no-dev --locked
```

Restart the web service after switching versions. A pinned checkout is detached; switch back to `main` before using
normal branch-based updates.
